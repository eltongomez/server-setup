# Git Configuration - Conventional Commits Format

## Convenção de Commits

Este repositório segue **Conventional Commits** (https://www.conventionalcommits.org/).

### Formato

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Tipos Permitidos

- **feat**: Nova funcionalidade
- **fix**: Correção de bug
- **docs**: Mudanças apenas em documentação
- **style**: Mudanças que não afetam código (formatação, espaços em branco)
- **refactor**: Refatoração de código sem mudar funcionalidade
- **perf**: Melhoria de performance
- **test**: Adição ou atualização de testes
- **chore**: Tarefas de manutenção, dependências, config
- **ci**: Mudanças em CI/CD
- **build**: Mudanças em sistema de build

### Scope (Opcional)

Área do código afetada:
- `security` - Segurança
- `backup` - Backup
- `monitoring` - Monitoramento
- `docs` - Documentação
- `ci` - CI/CD
- `ssh` - SSH hardening
- `firewall` - Firewall
- etc.

### Subject

- Use imperativo: "add" não "added"
- Não capitalize a primeira letra
- Sem ponto (.) no final
- Máximo 50 caracteres
- Português ou Inglês (escolha um e mantenha)

### Body (Opcional)

- Explique O QUÊ e POR QUÊ, não COMO
- Separe com uma linha em branco do subject
- Máximo 72 caracteres por linha
- Use bullet points se necessário

### Footer (Opcional)

- Referências a issues: `Closes #123`, `Fixes #456`
- Breaking changes: `BREAKING CHANGE: descrição`

### Exemplos

#### Simples
```
feat(ssh): adicionar suporte a porta customizável
```

#### Com body
```
fix(backup): corrigir falha ao restaurar backup em CentOS

O script falhava ao tentar restaurar backups em CentOS 7
devido a diferença no comando tar. Adicionada verificação
de distribuição antes de executar restauração.

Closes #42
```

#### Breaking change
```
feat(script)!: refatorar estrutura principal

BREAKING CHANGE: A estrutura de módulos foi refatorada.
Scripts antigos precisam ser atualizados para nova estrutura.
```

## Git Flow - Estratégia de Branching

Este repositório segue **Git Flow** (https://nvie.com/posts/a-successful-git-branching-model/).

### Branches Permanentes

#### main (production)
- Sempre estável e pronto para produção
- Cada commit é uma release
- Protegido: requer pull request + reviews

#### develop (development)
- Branch de integração
- Contém features prontas para próxima release
- Pode estar em desenvolvimento

### Branches Temporárias

#### feature/* (features novas)
```bash
git checkout -b feature/nova-funcionalidade develop
# Trabalhar e fazer commits...
git push origin feature/nova-funcionalidade
# Criar Pull Request para develop
```

#### bugfix/* (correções não-críticas)
```bash
git checkout -b bugfix/correcao-descritiva develop
# Trabalhar e fazer commits...
git push origin bugfix/correcao-descritiva
# Criar Pull Request para develop
```

#### hotfix/* (correções críticas em produção)
```bash
git checkout -b hotfix/critico-seguranca main
# Trabalhar e fazer commits...
# Fazer PR para main E develop
```

#### release/* (preparação de release)
```bash
git checkout -b release/1.1.0 develop
# Atualizar versão, CHANGELOG, etc.
# PR para main com tag
# Merge de volta para develop
```

## Workflow Padrão

### Para Desenvolver Feature Nova

```bash
# 1. Criar branch a partir de develop
git checkout develop
git pull origin develop
git checkout -b feature/descricao-feature

# 2. Fazer commits semânticos
git add arquivo.sh
git commit -m "feat(modulo): descrição da feature"

# 3. Push e criar Pull Request
git push origin feature/descricao-feature
# No GitHub: criar PR de feature/* para develop

# 4. Após aprovação: merge e cleanup
git checkout develop
git pull origin develop
git merge --no-ff feature/descricao-feature
git push origin develop
git branch -d feature/descricao-feature
git push origin --delete feature/descricao-feature
```

### Para Fazer Release

```bash
# 1. Criar branch de release
git checkout -b release/1.1.0 develop

# 2. Atualizar versão (package.json, script, CHANGELOG)
# Fazer commits de versioning

# 3. Merge para main com tag
git checkout main
git pull origin main
git merge --no-ff release/1.1.0
git tag -a v1.1.0 -m "Release v1.1.0"
git push origin main
git push origin v1.1.0

# 4. Merge de volta para develop
git checkout develop
git merge --no-ff release/1.1.0
git push origin develop

# 5. Cleanup
git branch -d release/1.1.0
```

## Configuração Local

### Configurar User Git

```bash
git config --local user.name "Seu Nome"
git config --local user.email "seu.email@dominio.com"
```

### Configurar Merge Strategy

```bash
# Usar --no-ff para manter história de branches
git config merge.ff false
```

### Hooks (Opcional)

```bash
# Copiar pre-commit hook
cp .git-hooks-pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

## Regras de Proteção (Branch Protection)

No GitHub, configurar:

### Para main
- ✅ Require pull request reviews (2 approvals mínimo)
- ✅ Require status checks (lint, tests)
- ✅ Require branches up to date
- ✅ Include administrators

### Para develop
- ✅ Require pull request reviews (1 approval)
- ✅ Require status checks
- ✅ Dismiss stale reviews

## Tags e Versionamento

Usar Semantic Versioning: `vMAJOR.MINOR.PATCH`

```bash
# Criar tag annotated (preferido)
git tag -a v1.0.0 -m "Release v1.0.0: Initial release"

# Ver tags
git tag -l
git show v1.0.0

# Deletar tag local
git tag -d v1.0.0

# Deletar tag remota
git push origin --delete v1.0.0
```

## Labels para Issues e Pull Requests

Criar labels no GitHub:

- `bug` (vermelho) - Problema/bug
- `enhancement` (azul) - Melhoria/feature
- `documentation` (amarelo) - Documentação
- `security` (laranja escuro) - Segurança
- `breaking-change` (vermelho escuro) - Mudança de breaking
- `good-first-issue` (verde claro) - Boa para iniciantes
- `help-wanted` (verde) - Precisa ajuda
- `question` (roxo claro) - Pergunta
- `wontfix` (cinza) - Não será resolvido
- `duplicate` (cinza claro) - Duplicada
